# Website & Growth Assessment — Backend Options (V1)

Status: Architecture Draft — Pending Owner Approval

## 1. Candidates Compared

1. **Cloudflare Workers** (with Durable Objects / Queues / D1 or KV as needed)
2. **AWS Lambda + API Gateway** (with SQS for async jobs, DynamoDB or RDS for storage)
3. **Vercel Functions**

A fourth option, Netlify Functions, is noted briefly in §5 but not compared in full depth — it shares most of Vercel's tradeoffs and does not change the recommendation.

## 2. Evaluation Table

| Criterion | Cloudflare Workers | AWS Lambda + API Gateway | Vercel Functions |
|---|---|---|---|
| SSRF-control capability | Strong — Workers has no implicit access to a private network by default; outbound `fetch()` goes over the public internet identically to any client, meaning the private-IP blocklist (`security-threat-model.md` §2) is the *only* thing standing between the Worker and an internal target — there is no additional cloud-VPC-internal risk to reason about. | Requires explicit care — a Lambda inside a VPC can reach VPC-internal resources unless network ACLs/security groups are configured correctly; a Lambda *outside* a VPC behaves similarly to Workers. Either way, the same application-level validation from §2 is required regardless of AWS networking config, so this is a wash if configured correctly, but has more ways to configure incorrectly. | Similar to Workers — no implicit private network access. Comparable SSRF posture to Workers. |
| Outbound-network controls | Full control via `fetch()`; can pin to a specific resolved IP for the DNS-rebinding mitigation (`security-threat-model.md` §1.2) using Workers' `fetch()` with a resolved-IP override pattern (connect via IP, set `Host` header/SNI manually), though this requires careful implementation since Workers' `fetch()` is Fetch-API-based, not raw-socket. | Full control via any HTTP client library (e.g., Node's `http`/`https` with explicit socket-level IP pinning) — arguably more mature tooling for exactly this pattern (IP-pinned connections) than Workers' Fetch-API constraint. | Similar constraint profile to Workers (Fetch-API-based runtime), same caveats. |
| DNS behavior | Workers' `fetch()` performs DNS resolution internally; achieving true "resolve once, validate, connect to that exact IP" requires either a DNS-over-HTTPS pre-resolution step (query DoH, validate the IP, then connect to the IP directly with `Host` header set) since Workers does not expose a lower-level socket API for arbitrary TCP by default (`connect()` API exists for TCP sockets in newer Workers runtime — this needs implementation-time verification of current API surface). | Full DNS control via standard Node.js `dns` module + raw socket/TLS connection — the most direct path to correctly implementing DNS-rebinding pinning (§1.2). | Same DNS/runtime constraints as Workers (Vercel Functions historically run on similar edge/serverless runtimes with comparable Fetch-API limitations, depending on Node vs Edge runtime selection). |
| Execution-time limits | Free/Standard: CPU time limited (tens of ms typical, extendable on paid plans); wall-clock time can extend further for I/O-bound work (fetch waiting doesn't count against CPU time the same way). Needs verification against current Cloudflare pricing tier for the 60s total-analysis budget (`crawl-specification.md` §17) — likely fine on a paid plan, needs confirmation for free tier. | Up to 15 minutes per invocation — comfortably exceeds the 60s budget with large margin, least constrained option. | Function execution limited (typically 10s–60s depending on plan) — tightest fit against the 60s total-analysis budget, least margin for error. |
| Memory/runtime constraints | 128MB typical Worker memory limit — adequate for streaming HTML parsing (5MB response cap) but requires care to avoid buffering full page content in memory unnecessarily. | Configurable up to 10GB — most flexible, least likely to hit a wall unexpectedly. | Typically 1GB or configurable depending on plan — adequate but less flexible than Lambda. |
| Async/background job suitability | Workers + Queues (Cloudflare Queues) supports async job patterns natively; Durable Objects can model the "analysis job in progress" state well. | Native fit via SQS + Lambda, very mature pattern for exactly this "submit job, poll/callback for result" architecture. | Vercel's serverless functions are less naturally suited to long-running background jobs; would likely need a separate queue service (e.g., a hosted queue or a second provider) bolted on. |
| Secrets handling | Cloudflare Workers Secrets (encrypted environment bindings) — solid, purpose-built. | AWS Secrets Manager / Parameter Store — mature, well-understood, slightly more setup overhead. | Vercel Environment Variables (encrypted at rest) — adequate, simplest to configure. |
| Rate limiting | Cloudflare has native rate-limiting rules at the edge (available on the same platform, no extra service needed) — a strong fit for `security-threat-model.md` §1.27. | Requires API Gateway usage plans / throttling configuration, or a separate mechanism (e.g., DynamoDB-backed counter) — more moving parts. | Requires a separate rate-limiting layer (e.g., Vercel Edge Config + custom logic, or a third-party service) — least native support of the three. |
| Caching | Cloudflare Cache API / KV is a natural fit for the 24-hour result cache (`crawl-specification.md` §17) and is on the same platform as the compute. | Requires a separate cache layer (ElastiCache/DynamoDB with TTL) — more infrastructure to stand up. | Vercel KV (Redis-based) available, reasonable fit, comparable setup effort to Cloudflare KV. |
| Observability/logging | Cloudflare Logpush / Workers Analytics — functional, somewhat less mature tooling than AWS CloudWatch's ecosystem for deep debugging. | CloudWatch Logs/Metrics/X-Ray — the most mature, feature-rich observability stack of the three. | Vercel's built-in logging/observability — functional for a smaller-scale service, less deep than CloudWatch. |
| Operational complexity | Low — single platform for compute, KV, queues, rate limiting; minimal infrastructure-as-code needed. | Higher — multiple AWS services to wire together (Lambda, API Gateway, SQS, DynamoDB/RDS, Secrets Manager, IAM roles) — more powerful but more to configure and maintain correctly. | Low-to-medium — simple for the compute layer itself, but async job support (per above) likely requires bolting on an additional service, adding complexity back. |
| Local development | `wrangler dev` provides a solid local dev loop with reasonable parity to production. | SAM CLI / LocalStack can approximate local Lambda dev but with more setup friction and less exact production parity than Workers' `wrangler`. | `vercel dev` is straightforward for the function layer; async-job bolt-on complicates local dev parity. |
| Integration with static Astro frontend | Cloudflare Pages (which the Astro site could be deployed to) integrates natively with Workers via Pages Functions / service bindings — very tight integration if the frontend were ever moved to Cloudflare Pages, though the current site is on SiteGround (a plain static host), so this advantage is currently theoretical rather than realized. | Works fine as a plain REST API called from any static frontend regardless of host — no special affinity to any particular static-host choice, which matches the current SiteGround-hosted reality more neutrally. | Vercel's tightest integration story is with a frontend *also* hosted on Vercel — since the Astro site is on SiteGround, this advantage is similarly theoretical. |
| Deployment complexity | Low — `wrangler deploy`, single command, single platform. | Higher — typically via CDK/Terraform/SAM for a multi-service stack; more powerful IaC ecosystem but more to write and maintain. | Low — `vercel deploy`, similar simplicity to Workers for the compute layer alone. |
| Cost model | Usage-based, generally very inexpensive at low-to-moderate volume; predictable. | Usage-based (Lambda invocations + API Gateway requests + supporting services), can be inexpensive at low volume but has more line items to add up (API Gateway is often the least-obvious cost driver in a Lambda architecture). | Usage-based, generally inexpensive at low volume, similar cost profile to Workers for the compute layer; async bolt-on adds an additional cost line. |
| Vendor lock-in | Moderate — Workers-specific APIs (Durable Objects, KV bindings) are not directly portable, though core `fetch()`-based logic is close to standard Web APIs and reasonably portable. | Moderate-to-high — deep integration with AWS-specific services (IAM, SQS, DynamoDB) makes a future migration more involved, though this is also the most "standard enterprise" choice if the business ever needs AWS-specific compliance certifications or integrations. | Moderate — similar Fetch-API-based portability to Workers for the compute layer, less lock-in on the storage side if a separate provider is chosen for persistence. |
| Maintenance burden | Low — single platform, few moving parts to patch/monitor. | Higher — more services means more surface area to monitor, patch, and reason about during incidents. | Low-to-medium, similar to Workers for the core function, with the async-job bolt-on adding ongoing maintenance. |
| Future scalability | Scales automatically and very well for this workload shape (short-lived, I/O-bound requests); Cloudflare's global edge network is a natural fit for a public-facing assessment tool with unpredictable geographic traffic. | Scales extremely well and is the most proven at large scale, though this workload does not obviously require AWS-scale infrastructure at V1 volume. | Scales well for the compute layer; the async-job bolt-on is the more likely future scaling constraint. |

## 3. Recommendation

**RECOMMENDED — PENDING OWNER APPROVAL: Cloudflare Workers**, with Cloudflare Queues for the async analysis-job pattern and Cloudflare KV for the 24-hour result cache.

Rationale:
- Lowest operational complexity and maintenance burden for a V1 feature of this scope.
- Native, on-platform fit for the two features that matter most for this specific workload: rate limiting (§1.27 in the threat model) and result caching (§1.25) — both available without adding a second vendor.
- Cost-effective at expected V1 volume.
- The DNS-rebinding-pinning implementation detail (§2, DNS behavior row) is a real open question that must be resolved during Phase A of `implementation-plan.md` before this recommendation can be considered final — if Workers' current runtime cannot cleanly support IP-pinned connections with the required rigor, AWS Lambda becomes the fallback recommendation specifically because Node's `dns`/socket APIs make that pattern more straightforward. **This is the single most important open technical spike required before implementation begins.**

## 4. Explicit Non-Recommendation Rationale

AWS Lambda + API Gateway is not recommended as the V1 default primarily because of operational complexity relative to the feature's scope — it is a fully capable option and would be the natural second choice if the DNS-rebinding spike (§3) rules out Workers.

Vercel Functions is not recommended primarily because of weaker native support for the async-job and rate-limiting patterns this feature specifically needs, requiring additional bolted-on services that erode its "simplicity" advantage over Workers.

## 5. Netlify Functions (Brief Note)

Shares Vercel's general profile (simple compute layer, weaker native async-job/rate-limiting support) and does not change the recommendation. Not evaluated in the same depth as the three primary candidates above since it does not introduce a materially different tradeoff.
